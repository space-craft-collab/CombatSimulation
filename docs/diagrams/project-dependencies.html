The modular monolith with grain interfaces extracted into Battles.Grains.Abstractions. Each module is a single project with Domain/ · Features/ · Infrastructure/ folders (ADR-0009). Arrows of dependency point downward — every project references the ones below it.

💡 Why extract the grain interfaces? A grain interface must inherit IGrainWithGuidKey and its DTOs need [GenerateSerializer] — both pull in Microsoft.Orleans.Sdk. Press the highlight button: the Orleans dependency only reaches Battles.* + the host. Catalog and Players never see an Orleans type, which keeps ADR-0002's promise intact.

2 · How data flows through one battle

From a client action to a durable record — and which project owns each hop.

Idle — press play.
1
Battles · Features/ endpoint

Client submits an action

A feature-local Minimal API endpoint (mapped by the host) resolves ILiveBattleGrain via IClusterClient and calls it.

2
Battles · Grains/ folder

Grain wakes (state in RAM)

Single-threaded, FIFO — one action = one message. State auto-persists to Azure Table Storage.

3
Catalog (via Catalog.Contracts)

Reads monster stats

Grain calls ICatalogQueryService through DI. A plain interface — no Orleans type crosses into Catalog.

4
Battles · Domain/ folder

Resolves the round

Pure domain rules apply damage, buffs, turn order. Returns a BattleEventDto delta.

5
SignalR → client

Broadcasts the delta

The round delta streams back to the live view. Then the grain waits for the next action (or a Reminder/Timer fires).

6
Players (via Players.Contracts)

On completion: updates W/L

Grain calls IPlayerStatsService — again a plain interface, no Orleans leak.

7
Battles · Infrastructure/ folder

Writes snapshot, deactivates

IBattleSnapshotWriter (intra-Battles) persists the final result to Azure SQL via EF Core, then the grain unloads.
